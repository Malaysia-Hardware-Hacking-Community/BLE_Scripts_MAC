# Governance

WAMBLE is a small project, so its governance is deliberately light. This page
says how decisions are made today. It will grow if the community does.

## Who decides

The project currently follows a maintainer-led model. The maintainer has the
final say on what goes in, with the goal of keeping WAMBLE small, correct, and
safe to use. Decisions are made in the open, in issues and pull requests, so the
reasoning is on the record.

## How changes are decided

- Most changes are agreed in the pull request or issue where they are proposed.
- Larger changes, such as a new tool or a change to shared behavior, should start
  as an issue so the idea can be discussed before code is written.
- When there are different views, the aim is to find something everyone can live
  with rather than to win a vote. If no agreement is reached, the maintainer
  decides and explains why.

## Becoming a maintainer

There is no fixed checklist. People who contribute good work over time, review
others' changes helpfully, and follow the [Code of Conduct](CODE_OF_CONDUCT.md)
may be invited to take on more responsibility, including commit access. If you
would like to help maintain the project, say so in an issue.

## Scope

WAMBLE reimplements the useful parts of the Linux BlueZ command-line tools for
macOS and Windows. Changes that fit that purpose are in scope. Changes that would
pull the project in a very different direction are better suited to a fork, and a
friendly fork is always a reasonable path.
